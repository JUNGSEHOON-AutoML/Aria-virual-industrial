# CNOTTA × ARIA — 오토파일럿 BuildSpec

작성 2026-10-13 · 기준 브랜치 `dt-dashboard-p6`(`157c364` 이후) → 작업 브랜치 `dt-cnotta` · 작업 규칙 `AGENTS.override.md`

## 0. 결론

CNOTTA 브랜드의 검사 공정 디지털 트윈 대시보드를 **M0부터 M6까지 Codex가 스스로 이어서 완성**한다. 사람이 확인하는 시점은 두 번뿐이다: M1 화풍(실제 GPU 화면), M6 최종 데모.

- 레퍼런스 영상을 따라 그리지 않는다. 레퍼런스 프레임 비교는 게이트에서 뺀다(파일은 gitignore 상태로 두되 사용하지 않음). 기준은 이 문서의 CNOTTA 디자인 시스템이다.
- 모든 게이트는 스크립트로 자동 판정한다(`tools/gates/m{n}.py` → `docs/autopilot/gates/m{n}.json`). 사람 눈으로만 판단하는 게이트는 M1의 화풍 하나다.
- M1 화풍 승인을 기다리는 동안 M2–M4를 계속 진행한다. 화풍 피드백은 토큰·프리팹 범위에서만 반영되도록 구조를 잡는다.

## 1. CNOTTA 디자인 시스템

### 1.1 브랜드 해석

로고는 둥근 고리에 홈이 하나 난 원형 마크(눈금 하나가 있는 다이얼)와 굵은 남색 워드마크다. 여기서 세 가지를 가져온다.

- **다이얼**: KPI는 숫자 카드가 아니라 고리형 게이지로 표시한다. 선택 핀도 물방울 대신 "홈 난 고리" 마커를 쓴다.
- **남색 + 페리윙클 2색 체계**: 무게는 남색이, 강조는 페리윙클이 맡는다. 레퍼런스처럼 진한 파랑으로 건물을 칠하지 않는다.
- **둥근 기하**: 모서리 반경을 크게, 선은 굵고 끝이 둥글게.

### 1.2 토큰 (`frontend/src/brand/cnotta.tokens.json`에 한 번만 정의)

로고 이미지에서 샘플링한 값을 기준으로 정했다. 원본 로고 파일을 받으면 `brand.ink`·`brand.primary`만 원본 값으로 바꾼다.

| 토큰 | 값 | 용도 |
|---|---|---|
| brand.ink | `#10295E` | 워드마크, 제목, 3D 설비의 짙은 포인트(다리 끝·받침) |
| brand.primary | `#5E66F4` | 강조, 선택, 벨트, 진행 막대, 다이얼 |
| brand.primary-100 | `#EEF0FE` | 선택 배경, 칩 배경 |
| brand.primary-200 | `#DDE1FD` | 구역 바닥 표시, 비활성 게이지 트랙 |
| surface | `#F7F8FC` | 앱 배경, 3D 외곽 지면 |
| floor | `#FFFFFF` | 건물 내부 바닥 |
| line | `#E3E6F0` | 통로선, 카드 경계 |
| equip | `#FFFFFF` + `#E9ECF5` | 설비 본체(흰색)와 프레임(연회색) |
| cardboard | `#D8B48C` | 박스 |
| human | `#F2A33A` | 작업자 조끼(사람 표시 전용) |
| foliage | `#7CC8A4` | 나무(채도 낮게) |
| ok / ng / hold | `#1FA971` / `#E5484D` / `#F5A524` | 판정에만 사용 |
| text-2 | `#5B6585` | 보조 텍스트 |

규칙: 판정 3색은 부품·판정 칩에만 쓴다. 한 화면에서 `brand.primary` 면적은 10% 이하로 한다. 나머지는 흰색·남색·회색이 맡는다.

### 1.3 형태와 빛

- 3D: 흰 설비 + 페리윙클 벨트 + 남색 받침. `RoundedBox` 반경 0.06–0.12. 건물은 흰 외벽에 남색 상단 띠, 높이 2.4m 이하의 절개 벽.
- 지면 `surface`, 건물 바닥 `floor`, 구역은 `primary-200` 반투명 바닥판과 둥근 모서리 경계선으로 표시한다.
- 빛: `NoToneMapping`, sRGB 출력. ambient 0.6 + hemisphere 0.4 + directional 0.9(그림자) + `ContactShadows` opacity 0.35. 렌더된 지면·바닥 픽셀이 토큰 값에서 채널당 ±6 이내여야 한다(자동 게이트).
- 카메라: 정사영, 방위 45°, 내려다보기 35°, 회전 ±20°, 클릭 시 0.6초 fly-to.
- UI: 카드 반경 16px, 그림자 `0 6px 24px rgba(16,41,94,0.08)`, 글꼴 Pretendard(기존 로컬 파일). 숫자는 tabular-nums.
- 브랜드 표시: 상단 바 좌측 CNOTTA 로고 + "ARIA Inspection Twin". 건물 외벽 한 곳에 로고 마크 데칼. 그 외 반복 노출 금지.
- 로고 파일: 원본이 없으면 마크(홈 난 고리)를 SVG로 임시 제작해 `frontend/public/brand/cnotta-mark.svg`에 두고 `DECISIONS.md`에 "임시 로고, 원본 교체 필요"로 기록한다.

## 2. 화면 구성

| 영역 | 위치 | 내용 |
|---|---|---|

| 다이얼 KPI 3개 | 좌상단 | 처리량/h, GT 기준 출하 품질률, 오탐/1,000. 고리 게이지 + 숫자 + 기준 모델 대비 Δ |
| 상세 카드 | 우상단, 선택 시 | 부품·설비·로봇·재검사 구역별 카드 |
| 재생 바 | 하단 중앙 | 재생/일시정지, 1×·10×·60×, 시간 슬라이더 |

| 자원 탭 | 우하단 | 설비·로봇·재검사 3탭, 상태 칩, 활용률 막대 |
| 비교 보기 | 우하단 탭 하나 | 모델별 오탐/1,000·인시/1,000·품질률, 95% CI |

패널은 캔버스 위 절대 위치이며 3D를 밀어내지 않는다. 기본 시점에서 패널이 가리는 3D 설비 면적은 15% 이하(자동 게이트).

## 3. 장면 배치

D0 평면 배치를 유지하되 아래를 바꾼다.

- 카메라를 당겨 라인·로봇 셀·재검사 구역이 기본 시점 화면의 70% 이상을 채운다.
- 재검사 구역을 본 라인에서 통로 1개(약 2m) 떼어 놓는다. NG 레인은 구역 입구의 대기 랙 앞에서 끝난다. 레인과 랙·작업대 바운딩박스 겹침 0.
- 라벨 칩은 INFEED·VISION·SORT·OFFLINE REINSPECTION·ROBOT CELL 다섯 개만 둔다. 좌상단 큰 제목은 제거한다.
- 폐기 빈은 위가 열린 상자 모양. 바닥 통로선과 구역선을 넣는다.
- 트럭·도로·나무는 장식이며 클릭되지 않는다. 트럭 측면에는 CNOTTA 마크만 넣는다.

## 4. 데이터 계약

새 읽기 전용 API. DES를 실행하지 않는다.

| API | 반환 |
|---|---|
| `GET /api/dt/runs` | 재생 가능한 실행 목록: run_id, 클래스, 모델, 셀·속도, 지연 모드, seed, 완료 hash |
| `GET /api/dt/runs/{id}/timeline?from=&to=` | 부품 구간(투입·검사·판정·분기·출구 시각, 경로, 판정), 설비 상태 전이, 재검사 대기열 시계열(기본 B 사후 결과) |
| `GET /api/dt/runs/{id}/kpi?t=` | 시각 t까지의 KPI. `evaluation.py`·`posthoc.py`와 같은 함수로 서버에서 계산 |
| `GET /api/dt/results/summary` | 본 실험 요약(95% CI). 없으면 404 → 화면은 "실험 진행 중" 표시 |

- 부품 위치는 구간 시각 사이를 레인 polyline으로 보간한다. 부품은 `InstancedMesh` 하나로 그린다.
- 재검사 랙의 박스 수 = 해당 시각의 사후 계산 대기열 길이. 랙 용량을 넘으면 바닥에 쌓고 숫자 배지.
- 개발·데모는 파일럿 실행(`docs/validation/aria_dt_20261013_03/des_pilot30/`)을 쓴다. 본 실험이 끝나면 결과 폴더만 추가한다.

M5는 본 실험이 끝나야 완료된다. 실험이 끝나기 전이면 M5를 BLOCKERS에 "실험 대기"로 두고 M6를 파일럿 데이터 기준으로 먼저 끝낸다.

## 9. 캠퍼스 맵

### 9.1 결론

큰 맵은 **장식이 아니라 비교 장치**로 만든다. 캠퍼스의 건물 하나는 검사 홀 하나이고, 각 홀 안에는 같은 부품 흐름을 받는 레인 3개(코어셋·CCIFPS·랜덤 동일-K)가 나란히 있다. 같은 시드의 부품이 세 레인에 동시에 들어가고, NG 레인과 재검사 랙이 모델마다 다르게 차오르는 모습이 한눈에 보인다. 홀은 클래스별로 3개(bottle·screw·carpet)다.

### 9.2 구조: 두 단계 시점

| 단계 | 보이는 것 | 진입 |
|---|---|---|
| 캠퍼스 | 홀 3개 + 로봇 셀 동 + 물류 야드 + 도로·나무, 각 홀 지붕 위 다이얼 배지(오탐/1,000) | 기본 시점, 상단 바 "캠퍼스" |
| 홀 | 레인 3개, 공유 투입부, 홀 전용 재검사 구역 | 홀 클릭 또는 상단 바 홀 선택, 0.8초 fly-to |

- 건물 지붕은 캠퍼스 시점에서 보이고, 홀 시점으로 들어가면 지붕이 페이드아웃된다(절개 벽 유지).
- 홀 시점의 패널(다이얼 KPI·상세 카드·자원 탭)은 해당 홀 기준이다. 캠퍼스 시점의 패널은 3개 홀 요약이다.
- 미니맵(우하단 작은 평면도, 현재 시야 사각형 표시)을 둔다. 미니맵 클릭으로 이동.

### 9.3 맵 정의는 데이터로

`frontend/src/campus/campus.layout.json` 하나가 맵 전체를 정의한다. 장면 코드는 이 파일을 읽어 조립만 한다.

```json
{
  "units": "m",
  "sites": [
    {"id": "hall-bottle", "kind": "inspection_hall", "class": "bottle", "origin": [0, 0], "rotation": 0,
     "lanes": ["coreset", "ccifps", "random_same_k"], "run_selector": {"seed": 0, "cell": "inline", "speed": 0.5}},
    {"id": "hall-screw", "kind": "inspection_hall", "class": "screw", "origin": [48, 0], "rotation": 0},
    {"id": "hall-carpet", "kind": "inspection_hall", "class": "carpet", "origin": [96, 0], "rotation": 0},
    {"id": "robot-cell", "kind": "robot_cell", "origin": [24, 40]},
    {"id": "yard", "kind": "logistics_yard", "origin": [72, 40], "decorative": true}
  ],
  "roads": [[[-20, -16], [140, -16]], [[60, -16], [60, 70]]],
  "foliage_seed": 7
}
```

- 홀 하나는 M1에서 만든 `Site` 컴포넌트를 재사용하되 레인 수를 `lanes` 길이만큼 늘린다. 홀 치수는 레인 수와 CAD `dims.json`에서 계산한다.
- 나무·박스·팔레트 배치는 `foliage_seed`로 고정한다. 새로고침해도 같은 맵이 나와야 한다.
- 장식 구역(`decorative: true`)은 클릭되지 않고 데이터와 연결하지 않는다.

### 9.4 데이터 연결

- 홀의 세 레인은 같은 클래스·셀·속도·시드의 세 모델 실행을 동시에 재생한다(`/api/dt/runs`에서 `run_selector`로 고름). 투입 스케줄이 같으므로 세 레인의 투입 부품 ID는 같아야 한다(자동 게이트).
- 캠퍼스 배지와 요약 패널은 `/api/dt/runs/{id}/kpi`를 홀별로 모은 값이다. 본 실험 결과가 있으면 `/api/dt/results/summary`의 30시드 평균과 95% CI를 쓴다.
- 재생 시계는 캠퍼스 전체가 하나를 공유한다.

## 10. 라이브 운영·에이전트·비전 분석

## 10.0 결론과 원인

현재 CNOTTA 화면은 실험 원자료를 재생하는 뷰어라서, 기존 ARIA가 하던 일이 화면에서 빠졌다. 실제 CCIFPS 추론과 히트맵 근거, 순찰 로봇의 이동·진단, M0609의 집기·검사·놓기, 고장 → 순찰 → 수리 → 재개 하네스, 공정 에이전트의 제안·승인이 모두 기존 저장소에 있는데 새 화면에 연결하지 않았다. 재생 전용으로 범위를 잡은 명세의 누락이다.

해결: 같은 CNOTTA 화면에 **모드 두 개**를 둔다.

| 모드 | 엔진 | 용도 | 숫자의 지위 |
|---|---|---|---|
| 운영(Live) | 기존 `aria/simulation/des/service.py` 라이브 DES + 실제 검출기 어댑터 + 순찰·수리·로봇·에이전트 | 살아 있는 공장 시연, 에이전트 수행 | `sim=1 · live`. 연구 결론에 쓰지 않음 |
| 실험(Replay) | 저장된 정책 A 실행 재생(M2–M5) | 모델 비교의 근거 | `sim=1 · replay`. 보고서 수치와 일치해야 함 |

상단 바에 모드 전환을 두고, 모드마다 배지를 바꾼다. 두 모드는 같은 장면·같은 프리팹을 쓴다.

## 10.1 기존 기능 재사용 목록 (먼저 읽을 파일)

| 기능 | 백엔드 | 기존 화면 | 이번에 할 일 |
|---|---|---|---|
| 라이브 DES·공정 편집 | `aria/simulation/des/engine.py`, `service.py`, `server/routers/factory.py` | `frontend/src/hmi/factory/FactoryScene.jsx` | CNOTTA 장면에 상태 스트림 연결 |
| 실제 검사·근거 | `aria/simulation/des/inspection.py`, `evidence.py`, `/api/factory/evidence/*` | `EvidenceWorkbench.jsx` | 상세 카드·근거 패널로 이식 |
| 로봇팔 작업 | `aria/simulation/des/robot.py`(7단계, `robot_ack`) | `RobotWorkbench.jsx`, `RobotArm.jsx` | 부품을 실제로 집어 옮기는 장면 연결 |
| 순찰·문제 보고 | `aria/simulation/des/patrol.py`(A* 경로, 현장 확인) | `PatrolHumanoids.jsx`, `PatrolPanel.jsx` | 4족 순찰 로봇 모델로 교체 |

기존 동작은 바꾸지 않고 화면과 연결한다. 백엔드 수정이 필요하면 기존 테스트 74개 이상과 골든 diff 0을 유지한다.

## 10.2 L1 — 비전 분석 리포트 (데이터셋에 어떤 문제가 있는지)

P1 결과(`per_image.csv`, 점수 맵, 임계값)로 클래스·모델별 진단 리포트를 자동 생성하고, 화면의 "비전 분석" 탭에서도 같은 내용을 보여 준다.

리포트 구성(`docs/reports/vision_audit/<class>/REPORT.md` + 그림, 화면 탭은 같은 JSON을 읽음):

1. **점수 분포**: 정상·불량 이미지 점수 히스토그램과 임계값 선. 두 분포가 겹치는 구간의 이미지 수.
2. **오탐 갤러리**: 정상인데 NG인 이미지 상위 k개(점수순). 원본, 히트맵, 최대 반응 패치 위치.
3. **미탐 갤러리**: 불량인데 OK인 이미지 전부. 원본, GT 마스크, 히트맵 비교.
4. **결함 유형별 성능**: MVTec 결함 하위 폴더(예: screw의 `thread_side`, `scratch_head`)별 탐지율과 평균 점수.
5. **오탐 원인 분류**: 오탐 이미지의 최대 반응 위치가 물체 마스크 안인지 밖(배경)인지. 학위논문의 배경 간섭 가설을 데이터로 확인하는 항목. 물체 마스크는 정상 이미지에서 고정 방법(Otsu 등, 방법을 리포트에 명시)으로 만들고, 방법의 한계를 적는다.
6. **모델 간 차이**: 세 모델이 다르게 판정한 이미지 목록과 각 모델의 점수.
7. **공정 영향 연결**: 위 오탐·미탐이 라인에서 1,000개당 몇 건의 재검사·유출이 되는지(사후 계산 결과 인용).

규칙:
- 점수 맵이 저장돼 있지 않은 이미지는 다시 계산해야 한다. **본 실험이 GPU를 쓰는 동안에는 CPU로만 계산**하고, 느리면 오탐·미탐·모델 간 차이 이미지로 범위를 줄이고 그 사실을 적는다.
- GT 마스크는 리포트 표시에만 쓴다. 검출기 입력이나 임계값에 쓰지 않는다.
- "원인"은 단정하지 않는다. "최대 반응이 배경에 있었던 오탐 비율 n/m"처럼 측정값으로 쓴다.

게이트: 3클래스 × 3모델 리포트 생성, 리포트 수치 = `per_image.csv` 재집계, 갤러리 이미지의 점수·판정 = CSV, 화면 탭과 리포트 JSON 동일.

## 10.3 L2 — 운영 모드: 살아 있는 공정

- 라이브 DES 상태를 WebSocket으로 받아 CNOTTA 장면의 부품·설비·로봇을 움직인다. 화면 자체 타이머로 공정을 만들지 않는다는 원칙은 그대로다(라이브 DES가 시계).
- 검사 셀은 실제 검출기 모드(`ccifps`)로 돌린다. 부품마다 실제 이미지가 배정되고, NG 판정 부품을 클릭하면 실제 히트맵 근거가 열린다.
- **로봇팔이 실제로 일을 한다**: 로봇 셀에서 M0609가 부품을 집어(그리퍼 CLOSED 동안 부품이 TCP를 따라감) 카메라 앞에 들고, 검사 결과가 나온 뒤 판정에 맞는 자리(OK 트레이 / NG 슈트)에 놓는다. `robot_ack` 7단계와 화면 동작이 일치해야 한다.
- 고장 주입 → 설비 DOWN → 순찰 로봇 출동 → 현장 확인 → 수리 하네스 단계(진단·도구·재검사·인터록 해제) → 공정 재개가 장면에서 이어서 보인다.

게이트: 로봇이 놓은 부품 ID = 그 직전 검사 부품 ID, 놓은 위치 = 판정, 그리퍼 OPEN 상태에서 부품 이동 0. 고장 시나리오 10 seed에서 출동 → 확인 → 복구 → 재개 이벤트 순서 보존. 화면 진행 부품 수 = 라이브 스냅샷.

## 10.4 L3 — 에이전트 작업 카탈로그

ARIA 에이전트(기존 `IndustrialAgent` + MCP 도구)가 이벤트를 보고 **장면 안에서 수행되는 작업**을 발행한다. LLM(로컬 Ollama)이 없어도 규칙 기반으로 모든 작업이 돌아야 하고, LLM은 문장 생성·의도 분류에만 쓴다. KPI 숫자는 항상 도구 결과에서 가져온다.

| 작업 | 트리거 | 에이전트 행동 | 장면에서 보이는 것 | 사람 승인 |
|---|---|---|---|---|
| A1 고장 대응 | 설비 DOWN | 가장 가까운 순찰 로봇 배정 → 진단 → 수리 하네스 실행 | 로봇 출동·작업 애니메이션, 설비 상태 칩 변화 | 불필요(가상 수리) |
| A2 품질 이상 | 최근 N개 NG 비율이 기준선 대비 상승(N, 기준은 config, assumed) | 해당 구간 근거 히트맵 수집 → L1 방식으로 배경 반응 비율 계산 → 원인 후보와 조치 제안(임계값 재보정 / 뱅크 재구축 / 조명 점검) | 검사 부스 경고 마커, 근거 카드 | **조치 적용은 승인 필요** |
| A3 재검사 적체 | 재검사 대기열이 기준 초과 | what-if 실험(기존 experiments API)으로 인원 +1 / 라인 감속 비교 → 제안 | 재검사 구역 경고, 비교 카드 | 승인 필요 |
| A4 NG 재촬영 | 점수가 임계값 근처(±δ, config)인 NG | 로봇팔에 재검사 작업 발행: 집어서 다른 자세로 다시 제시 → 같은 이미지 재판정은 하지 않음. 재촬영 데이터가 없으면 "추가 촬영 필요"로 사람 재검사 큐에 우선 배정 | 로봇팔 재제시 동작, 부품 경로 변경 | 불필요 |
| A5 교대 보고 | sim 시간 N분마다 | 처리량·오탐·미탐·고장·조치 요약 보고서 생성(Markdown, 다운로드) | 메시지 패널 알림 | 불필요 |

- 모든 에이전트 결정은 `agent_events.jsonl`에 관측·판단·도구 호출·결과로 남고, 화면 메시지 패널에서 타임라인으로 보인다(OODA 표시).
- A2의 "임계값 재보정"을 승인하면 샌드박스 bundle에만 적용하고, 정상 holdout으로만 재보정한다. 테스트 이미지로 임계값을 고르지 않는다.
- A4에 대해: MVTec는 다시점 이미지가 없다. 재촬영으로 판정이 바뀌는 것처럼 보이게 만들지 않는다. 이 한계를 카드에 표시한다.

게이트: 작업 5종을 각각 일으키는 고정 시나리오 5개가 결정론적으로 재현(같은 seed → 같은 agent_events), 승인 필요 작업이 승인 없이 적용된 횟수 0, 메시지 패널 숫자 = 도구 결과, LLM 비활성 상태에서도 5개 통과.

## 10.5 L4 — 4족 순찰 로봇

- 기존 휴머노이드 순찰 로봇을 4족 로봇 모델로 바꾼다(코드로 만든 저폴리 모델: 몸통, 다리 4개 각 2관절, 머리 센서). 실존 제품의 외형을 복제하지 않는다. 몸통에 CNOTTA 마크.
- 이동은 기존 `patrol.py`의 A* 경로를 따르고, 다리는 이동 속도에 맞춘 절차적 보행(trot) 애니메이션으로 움직인다. 물리 보행 시뮬레이션이 아님을 표시한다.
- 상태: PATROL / DISPATCHED / INSPECTING / REPAIRING / RETURNING. 머리 센서 색과 상단 칩으로 표시.
- 현장 확인 시 설비 앞에서 정지 → 센서 스캔 이펙트 → 확인 이벤트.

게이트: 경로가 설비 점유 영역과 겹친 프레임 0, 정지 중 다리 위상 고정, 상태 전이 = patrol 이벤트, 로봇 2대 동시 운용.

## 10.6 순서 (갱신)

M1 → M2 → **L1 → L2 → L3 → L4** → M3 → M4 → M5 → M6 → M7.

L1은 GPU를 쓰지 않는 범위에서 바로 시작할 수 있으므로 M2와 병행해도 된다.
