# ARIA 디지털 트윈 재설정 명세 v3

작성일: 2026-10-13 Asia/Seoul. 상태: 구현 전 개정안.

ARIA의 중심 작업을 **검사 모델 선택 → 동일 공정 실행 → 부품 판정 추적 → 품질·지연·비용 비교**로 통합한다. 기존 DES, CCIFPS, 실측 입력과 연구 원자료를 보존하면서 실행 설정과 화면 진입점을 정리한다. 이 문서의 목표 계약은 구현 완료 상태를 뜻하지 않는다.

## 1. 재설정의 범위

기본 작업 공간은 Inspection Lab이다. 기존 Factory와 QC Live는 명시적으로 이동할 수 있는 보조 작업 공간으로 유지한다. 공장 상태 초기화와 연구 데이터 삭제를 구분하며, 새 실행은 새로운 시뮬레이션 상태만 생성한다.

AGENTS.md, TOOLS.md, SKILL.md, 기존 검증 보고서, 데이터 링크, 특징 캐시, 뱅크, 실험 원자료는 보존한다. 첨부 PDF의 작업 지시 템플릿과 과거 보고서에 적힌 승인을 현재 실행 권한으로 사용하지 않는다.

신규 모델 학습, 물리 엔진 이전, 실제 PLC 제어, 모델 자동 다운로드, 데이터 삭제는 이 재설정의 대상이 아니다. LLM 없이도 replay와 평가가 실행되어야 한다.

## 2. 확인한 기준 상태

| 영역 | 현재 상태 | 전환 목표 |
|---|---|---|
| 명세 | 첨부 원문 외에 v2.0 HTML·PDF가 존재 | 연구 계약은 v2를 참조하고 이 문서에서 실행 구조 전환을 정의 |
| 화면 진입 | 기본 Control Tower, `?view=dt`에서 DT 화면 | 기본 DT, 기존 화면으로 명시적 이동 |
| DT 입력 | `server/routers/dt.py`의 P1 경로가 날짜별 검증 폴더에 고정 | 한 곳에서 입력·결과·라인 설정 경로 정의 |
| 실행 상태 | Preview 객체가 엔진·원장·설정 관리 | 모든 입력 검증과 엔진 생성 성공 후 상태를 한 번에 교체 |
| 결과 표시 | completion 파일 존재로 완료 표시 | 완료 표시와 실제 검증 상태를 구별 |
| 연구 엔진 | 지연·replay·평가기·사람 oracle 구현 존재 | 기존 의미와 결정론 보존 |
| 코드 기준 | HEAD 외에 수정·미추적 파일 다수 | 현재 작업 파일을 기준으로 변경하고 기존 작업 보존 |

이번 조사에서 기존 `tests/test_dt_latency.py`와 `tests/test_dt_replay.py`를 실행해 **24 passed**를 확인했다. 이는 재설정 구현이나 전체 연구 게이트의 통과를 뜻하지 않는다.

## 3. 연구 계약

동일 특징과 검색 설정에서 PatchCore coreset, CCIFPS, random_same_k를 비교한다. random_same_k는 CCIFPS의 실제 K에 맞춘 대조군이다. coreset의 K가 다르면 전체 방법 비교로 해석하고 동일-K 선별 효과라고 주장하지 않는다.

논문 재현과 ARIA 공정 실험은 별도 트랙이다. 정상 calibration으로 고정한 임계값을 사용하며 테스트 GT로 모델이나 임계값을 선택하지 않는다. 실측값, 가정값, 추정값, 화면 예시를 구별한다.

GT 접근은 소스 스케줄을 사전 작성하는 평가기, 사후 평가기, 가정 인간 판정을 만드는 `reinspect_oracle`에 한정한다. AI replay는 이미지 ID에 대응하는 저장 판정만 소비한다. GT가 없는 정책 B는 오류로 처리한다.

정책 A는 NG를 폐기한다. 정책 B는 NG를 본 라인을 막지 않는 오프라인 무제한 FIFO와 사람 재검사에 넘긴다. 기본 사람 모델은 민감도·특이도 1.0과 30초의 가정이다. HOLD는 기한 초과 격리이며 늦게 도착한 결과로 다시 분기하지 않는다.

인라인 검사 기한은 `distance_m / speed_m_s - actuator_s`이다. 0 이하인 기한은 실행 전에 거부한다. 지연 프로파일의 밀리초와 DES의 초를 명시적으로 변환한다. 화면 시계나 실제 실행 시간으로 replay 지연을 다시 계산하지 않는다.

## 4. 실행 설정 계약

DT 설정 모듈에서 P1 입력 루트, 결과 루트, 라인 프로파일, 미리보기 프로파일 저장 루트를 정의한다. 환경변수로 경로를 재지정할 수 있게 하되 상대 경로는 저장소 루트를 기준으로 해석한다. 기본값은 현재 유효한 입력을 가리키며 예전 무효 실험으로 자동 대체하지 않는다.

실행 전 확인할 항목은 선택 클래스·모델의 예측 CSV, 지연 프로파일, GT, 완료 manifest와 입력 hash, 라인 파라미터의 값·단위·출처다. 실패하면 누락 또는 불일치 항목을 반환한다. 파일 경로가 존재한다는 사실만으로 연구 검증 통과를 선언하지 않는다.

새 실행 요청은 임시 지역 객체에서 입력 검증, 소스 스케줄, oracle, 원장, 엔진을 모두 만든다. 성공했을 때만 기존 실행을 교체한다. 실패한 요청은 기존 실행의 설정·원장·엔진을 섞거나 초기화해서는 안 된다.

여러 사용자와 여러 worker가 공유하는 실행 서비스는 후속 범위다. 현재 단일 Preview의 소유권 제한을 문서화하고 한 API worker로 실행한다.

## 5. 화면 계약

첫 화면에 연구 목적, `sim=1`, 입력 준비 여부와 새 실행 동작을 표시한다. 준비되지 않은 경우 원인과 필요한 파일을 보여 준다. 자동으로 가짜 KPI를 생성하거나 측정된 다른 클래스 결과를 대체하지 않는다.

상단에는 클래스·모델·정책과 시뮬레이션 시계를 둔다. 공정 조건에는 셀 종류·속도·지연 모드를 둔다. 설정 변경으로 실행을 재시작한다는 사실을 표시한다. 사용자가 편집 중인 설정을 이전 snapshot 응답으로 덮어쓰지 않도록 요청 순서를 관리한다.

처리량, GT 출하 품질률, HOLD 비율은 API와 같은 시점의 값을 표시한다. 미리보기 누계와 600초 워밍업을 제외한 최종 실험 지표를 분리한다. 결과가 없거나 실패했을 때 0으로 표시하지 않는다.

부품 선택은 이미지·히트맵·점수·임계값·판정·경로·지연·기한을 연결한다. 부품 이동과 공정 단계는 DES 상태를 표현하며 렌더링 타이머로 판정을 생성하지 않는다. 자원 탭은 본 라인 처리량과 오프라인 재검사 대기 부하를 구별한다.

모델 비교는 같은 클래스·셀·속도·정책·지연 조건에서 중복 없는 30개 seed가 있는 그룹만 최종 95% CI로 표시한다. 부분 결과는 부분 결과로 표시한다. 세 모델의 순위나 성능 개선을 미리 정하지 않는다.

## 6. 실험과 인수 기준

전체 연구 계획은 기본 5,400회와 민감도 1,620회로 총 7,020회다. 클래스는 bottle·screw·carpet, 각 조건은 30 seed와 3,600초, 워밍업은 600초다. 비용 비율 5:1·20:1·100:1은 후처리한다. 모델 간 차이는 같은 seed의 짝지은 차이 CI로 평가한다.

기존 수정 파일럿 보고서는 전체 실행 비용을 13.49시간·62.48GB로 추정하고 본 실행을 보류했다. 이 수치는 기존 보고 기록이며 이번 작업의 측정 결과가 아니다. 재설정 성공과 전체 실험 완료는 별도로 판정한다. 성능·로그 최적화 후에도 새 파일럿으로 비용을 다시 평가해야 한다.

| 게이트 | 통과 기준 |
|---|---|
| 기존 동작 보존 | 지연·replay 회귀, constant 기준 추적, 기존 DES 불변식 통과 |
| 설정 분리 | 다른 입력 루트로 실행 가능하고 잘못된 경로·hash는 실행 전 실패 |
| 상태 교체 | 새 실행 실패 후 기존 엔진·설정·원장 유지 |
| 화면 진입 | 기본 DT와 기존 화면 이동, production build 성공 |
| 결과 정직성 | 입력 미준비·부분 결과·검증 완료를 구별하고 API 실패를 표시 |
| 실험 완료 | 계획 조건 수·원자료 hash·보존식·30 seed·보고서 확인 |
| 화면 성능 | 실제 GPU 브라우저 영상과 콘솔 검사; 소프트웨어 렌더링은 별도 기록 |

## 7. 구현 순서와 변경 대상

1. 실행 설정과 준비 상태 API를 분리하고 날짜 경로 의존성을 한곳으로 모은다. 대상은 새 DT 설정 모듈과 `server/routers/dt.py`다.
2. Preview 시작을 원자적 상태 교체로 바꾸고 실패 시 보존을 검사한다. 연구 엔진의 판정·난수 의미는 유지한다.
3. `frontend/src/hmi/AppShell.jsx`와 `frontend/src/features/dt/DTDashboard.jsx`에서 기본 진입, 이동, 준비 상태, 요청 오류를 정리한다.
4. README에 단일 실행 명령과 환경변수, 보존되는 데이터, 실행 모드와 한계를 기록한다.
5. 변경별 회귀와 빌드를 실행하고 실제 통과·실패·미검증 항목을 보고한다. 전체 실험과 GPU 측정은 별도 게이트로 남긴다.
